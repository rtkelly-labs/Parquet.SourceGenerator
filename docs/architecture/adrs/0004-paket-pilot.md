# ADR 0004: Paket Pilot for NuGet Dependency Management

> Companion to [CI Gate Matrix](../../internals/ci-gate-matrix.md) (the Paket lock, outdated-report
> and dependency-submission rows) and to CONTRIBUTING, "Changing a dependency". This page records
> why the repository is trying Paket, what the evaluation found, what the pilot changes, and how
> the rest of the migration is staged.

## Decision

Adopt [Paket](https://fsprojects.github.io/Paket/) in phases, starting with a pilot on one leaf
project. The repository owner decided this after an evaluation of Paket 11.0.1. This is not a full
migration: every project except the pilot keeps Central Package Management
(`Directory.Packages.props`) and its committed `packages.lock.json`, and Dependabot keeps updating
them.

The problem being solved: Dependabot's NuGet updater writes a broken `packages.lock.json` for the
multi-targeted `src/Parquet.SourceGenerator.Attributes` project. It writes only the
`netstandard2.0` section and drops `netstandard2.1`, `net8.0` and `net9.0`, so every Dependabot
NuGet pull request fails the locked restore with `NU1004` and needs the lock files regenerated by
hand on its branch (#696, #698 to #700, #705; the manual fix is documented by #707). Paket keeps one
lock for the whole repository and rewrites it correctly for every target framework.

## Evaluation findings

From a spike with Paket 11.0.1 on a scratch copy of this repository's dependency shape:

- **Per-framework references.** Groups handle them. A group with `restriction: == netstandard2.0`
  limited `System.Memory` and `Microsoft.Bcl.AsyncInterfaces` to `netstandard2.0` only, which is
  what the Attributes project needs.
- **Two Roslyn versions in one solution.** A `ShippedGenerator` group pinned
  `Microsoft.CodeAnalysis.CSharp` 4.0.1 (the shipped generator's floor, #432) while the tests used
  4.8.0.
- **Version operators.** `~> 4.8.0` blocks the major bump; `>= x` lets `paket update` move the
  lock; a bare version is a pin.
- **Updates.** `paket outdated` and `paket update` work, and `paket update` rewrote the lock
  correctly for several target frameworks.
- **Strict restore.** `dotnet paket restore --fail-on-checks` exits 1 when `paket.dependencies` and
  `paket.lock` are out of sync. Plain `paket restore` exits 0 and silently ignores the drift, and so
  does the restore that MSBuild runs through `Paket.Restore.targets`. CI must therefore run the
  strict form explicitly.
  Found during the pilot: once a restore has succeeded, the restore cache
  (`paket-files/paket.restore.cached`, keyed on `paket.lock`'s hash) short-circuits even the strict
  form, which then exits 0 on drift unless `--force` is added. CI is unaffected (a fresh checkout
  has no `paket-files/`, which is ignored and never committed); locally, use `--force`.
- **Vulnerability audit.** `dotnet list package --vulnerable` still works on Paket-managed
  projects. Paket hooks into `dotnet restore` through `.paket/Paket.Restore.targets`, and NuGet
  still writes `obj/project.assets.json`.
- **The converter fails here.** `paket convert-from-nuget` cannot parse
  `$(GeneratorPackageVersion)` in the package-consumption projects, so migration is by hand.
- **Ecosystem support.** Dependabot and Renovate do not support Paket. GitHub's dependency graph
  does not parse Paket either, so it needs a dependency submission to keep seeing Paket-managed
  packages (and security alerts on them).

## What the pilot changes

**Scope: `benchmarks/Parquet.SourceGenerator.Benchmarks` only.** It is a leaf: nothing in the
solution references it, so moving it puts Paket on the path of the solution restore and
`benchmarks.yml`, and nowhere else. `tools/BenchmarkSummaryGenerator` was considered and left out:
it has no package references of its own, but `test/Parquet.SourceGenerator.Tests` references it,
so migrating it would make every build of the test project (the `generated-analysis` job,
`scripts/DerivedOutputs.cs`, Stryker, a contributor's plain `dotnet test`) depend on Paket. It
moves with the test projects' group.

- **Tooling.** Paket 11.0.1 is a local tool in `.config/dotnet-tools.json` (`rollForward: false`,
  like the others). It targets `net10.0`, so a job that runs it installs the .NET 10 SDK.
- **`paket.dependencies`** (root): nuget.org, `storage: none` (packages stay in the NuGet global
  packages folder, nothing is copied into the repository), `framework: net8.0`, and
  `strategy: min`, which resolves transitive dependencies to the lowest version that satisfies them,
  as NuGet does. Direct references use `~>` ranges that contain today's versions
  (`BenchmarkDotNet ~> 0.14.0`, `Microsoft.CodeAnalysis.CSharp ~> 4.8.0`, `Parquet.Net ~> 6.1`).
  Four packages that are only transitive for the benchmarks are listed as floors, because Central
  Package Management's transitive pinning raised them and without it they would resolve lower:
  `CommandLineParser`, `Microsoft.Bcl.AsyncInterfaces`, `Microsoft.CodeAnalysis.Analyzers`,
  `System.Memory`. One group (`Main`) is enough for the pilot; the per-framework and
  second-Roslyn groups arrive with the projects that need them.
- **`paket.lock`** and **`.paket/Paket.Restore.targets`** (both generated by Paket) are committed.
  `paket-files/` and `.paket/*.cached` are ignored. `paket.dependencies`, `paket.lock` and `.paket/`
  are protected paths (`.github/protected-paths.txt`), like `Directory.Packages.props`.
- **The project.** `paket.references` names `BenchmarkDotNet`, `Microsoft.CodeAnalysis.CSharp` and
  `Parquet.Net`; the csproj lost its `PackageReference` items and imports
  `.paket/Paket.Restore.targets`; its `packages.lock.json` is deleted. `Directory.Build.props` sets
  `IsPaketManaged` for any project with a `paket.references`, and for such a project
  `Directory.Packages.props` turns Central Package Management off and drops its `PackageVersion`
  items (Paket supplies its own, which would otherwise duplicate them, `NU1506`), and
  `Directory.Build.props` skips the analyzer and SourceLink references it adds to other projects.
  The benchmark project received none of those anyway (it is under `benchmarks/` and not packable);
  a later project that does must list them in its `paket.references`, with `copy_local: true`,
  which is how Paket spells `PrivateAssets="All"`.
- **No version drift.** The benchmark project's `obj/project.assets.json` resolves the same 40
  libraries at the same versions before and after (38 packages and 2 project references, compared
  name by name and version by version).

### Locking and CI

Every job that restores the solution or the benchmark project runs `dotnet tool restore`, then
`dotnet paket restore --fail-on-checks`, then `dotnet restore ... --locked-mode`: `ci.yml` (`test`,
`derived`), `benchmarks.yml` (both jobs), `fuzz.yml`, `metrics-oracle.yml`, `mutation.yml`,
`release.yml` and `dependency-submission.yml`. In `ci.yml`'s `test` job the tool restore moved
up, ahead of the solution restore, which now calls Paket. `CiGateIntegrityTests` enforces both
halves:

- every solution project has exactly one of `packages.lock.json` or `paket.references` (the Native
  AOT projects have neither), and a project with `paket.references` imports
  `Paket.Restore.targets`;
- in every workflow job, each `dotnet restore` comes after a `dotnet paket restore
  --fail-on-checks` step, which comes after `dotnet tool restore`.

`benchmarks.yml` installed only .NET 8 before. It now installs .NET 10 for Paket, and the headline
suite's run step sets `DOTNET_ROLL_FORWARD: Minor` (as the regression gate already did) so the
benchmarks themselves stay on .NET 8.

### Updates without Dependabot

Dependabot keeps `nuget` on: it still covers every other project. It does not read Paket, so it no
longer sees the benchmark project's packages. In its place, `paket-outdated.yml` runs weekly (and
on dispatch) and keeps one issue labelled `paket-outdated`. The issue is open while
`dotnet paket outdated` finds a newer version inside the ranges (what `dotnet paket update` would
take) and is closed by the workflow once it finds none. Newer versions outside the ranges, from
`--ignore-constraints`, are listed for information; taking one is a deliberate range edit. The job
that runs Paket has a read-only token; the job with `issues: write` runs no repository code.

### Security alerts without the static graph

`dependency-submission.yml` runs on push to `main` (and dispatch on `main`), restores, and submits
the resolved NuGet graph with `advanced-security/component-detection-dependency-submission-action`
(SHA-pinned, NuGet detectors only, `fail-on-empty`). It needs `contents: write`, which the
submission API requires; it never runs on pull requests, and the only repository code it executes
is the restore. Two caveats: the action downloads the latest `microsoft/component-detection`
release when it runs, so that binary is not pinned; and component detection also parses
`paket.lock` directly and reports the lower bound of each dependency range as a component (for
example `System.Memory 4.5.1` from `Microsoft.Extensions.Primitives`' `>= 4.5.1`), which can
over-report. A local run of component-detection v8.0.5 over a restored checkout found all 38
packages of the benchmark project from its `project.assets.json`.

## Phased plan

1. **Pilot** (this change): the benchmark project, the strict restore in CI, the integrity rules,
   the outdated report and the dependency submission. Watch the submission on `main` and confirm
   the benchmark packages appear in the dependency graph (Insights, Dependency graph) with the
   versions in `paket.lock`.
2. **The remaining projects, group by group.** Each step moves one set of projects that share
   frameworks and versions into a Paket group, deletes their `packages.lock.json` and proves the
   resolved versions are unchanged, as the pilot did:
   - tools and the test projects (with `tools/BenchmarkSummaryGenerator`), with Roslyn 4.8.0 and
     the analyzers (`copy_local: true`);
   - the shipped generators, in a `ShippedGenerator` group pinning `Microsoft.CodeAnalysis.CSharp`
     4.0.1;
   - the multi-targeted Attributes project, with a `restriction: == netstandard2.0` group for
     `System.Memory` and `Microsoft.Bcl.AsyncInterfaces`. This is the project Dependabot breaks,
     and the one this whole migration is for.
   The package-consumption and Native AOT projects stay as they are: they carry no lock today and
   the converter cannot read the first.
3. **Retire the old mechanism** once the dependency submission is proven to keep security alerts
   on Paket-managed packages: remove the last `packages.lock.json`, `Directory.Packages.props` and
   the `nuget` entry in `.github/dependabot.yml` (keeping `github-actions`), and drop the
   lock-file half of the integrity rule.

The pilot is reversible: restoring the three `PackageReference` items and the benchmark
project's `packages.lock.json`, and deleting the Paket files and workflows, returns to the
previous state.

## Verification

- `dotnet tool restore --disable-parallel`, `dotnet paket restore --fail-on-checks` and
  `dotnet restore Parquet.SourceGenerator.slnx --locked-mode` pass; no other lock file changes.
- Release builds of the benchmark and test projects with `-warnaserror`: 0 warnings, 0 errors.
- `project.assets.json` of the benchmark project: 40 of 40 libraries identical before and after.
- Negative controls: adding a package to `paket.dependencies` without `paket install` makes
  `--fail-on-checks` exit 1 (on a checkout with no `paket-files/`, as in CI, or with `--force`); deleting the benchmark project's `paket.references`, or removing the
  strict Paket restore step from `ci.yml`, fails `CiGateIntegrityTests`.
