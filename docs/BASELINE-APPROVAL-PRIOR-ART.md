# Prior art for approving generated baselines

This note compares workflows for generated files, visual snapshots, and reference output. **Facts** below come from first-party documentation, source repositories, and maintainer posts. **Recommendations** are design choices for this repository, not claims that the cited tools implement them.

## What existing tools approve

| Tool | Candidate and comparison oracle | Review and enforcement |
| --- | --- | --- |
| Playwright | `toHaveScreenshot()` compares a run with reference screenshots; `toMatchSnapshot()` also handles text and binary data. Reference files live beside tests and are meant to be committed and reviewed in version control. `--update-snapshots` refreshes them. | Approval is a source diff and commit, with any PR gate supplied by the repository. Playwright warns that screenshots depend on the rendering environment. [Visual comparisons](https://playwright.dev/docs/test-snapshots) |
| Loki | The open-source Storybook tool tests screenshots against reference images, and `loki approve` updates references. Its README recommends Chrome in Docker for reproducible results. | Like Playwright, the reference is a file reviewed through source control; the tool itself does not supply a hosted PR approval state. [Loki README](https://github.com/oblador/loki) |
| Rust insta | Changed snapshots become pending `.snap.new` files beside committed `.snap` files. `cargo insta review` shows each diff and accepts, rejects, or skips it. Insta also documents uploading pending snapshots as CI artifacts. | Acceptance changes the reference file; a subsequent test against that file supplies the gate. Its CI artifact example is a way to retrieve candidates, not a durable baseline store. [Quickstart](https://insta.rs/docs/quickstart/), [CLI](https://insta.rs/docs/cli/), [CI artifact pattern](https://insta.rs/docs/patterns/) |
| Chromatic | UI Tests compare a build against the last accepted baseline in its Git-aware branch history; UI Review separately shows the PR head against the merge base. Accepted baselines live in Chromatic, not as committed screenshot files, and follow branches on merge. | Reviewers accept or deny changes in the UI. Unreviewed changes keep the PR check pending when that check is required; acceptance updates the baseline and check. [Branches and baselines](https://www.chromatic.com/docs/branching-and-baselines/), [PR workflow](https://www.chromatic.com/docs/in-pull-request/), [mandatory checks](https://www.chromatic.com/docs/mandatory-pr-checks/) |
| Argos | The first-party maintainer account describes PR screenshots compared with the approved build at the branch's merge base. Argos also accepts text artifacts, including Markdown, JSON, YAML, and HTML, and diffs them against a baseline. | Its review UI supports verdicts and comments. Argos says it maintains one current PR comment and posts a commit status that branch protection can require; selected main-branch builds can be auto-approved as baselines. [Maintainer comparison guide](https://argos-ci.com/blog/screenshot-testing-guide), [Argos Diff](https://argos-ci.com/diff), [Argos Review](https://argos-ci.com/review) |
| reg-suit | The open-source CLI fetches expected images from external storage, such as S3 or Google Cloud Storage, and publishes current captures and a diff report. Its Git-based key plugin identifies the comparison commit. | Its GitHub plugin updates an existing PR comment by default, posts a commit status, and lets a reviewer approve intended visual changes. [reg-suit README](https://github.com/reg-viz/reg-suit/blob/master/README.md), [GitHub notifier](https://github.com/reg-viz/reg-suit/blob/master/packages/reg-notify-github-plugin/README.md) |

The first-party [Storybook visual-testing post](https://storybook.js.org/blog/visual-testing-is-the-greatest-trick-in-ui-development/) describes the common loop: capture, compare, inspect the PR result, then accept an intended change as the next baseline. Chromatic's branch-history model and Argos's merge-base model show why **the latest PR artifact is a candidate, not the oracle**. A PR can be regenerated many times before approval; comparison still needs the previously approved state. Chromatic also documents that UI Tests and UI Review answer different questions: regression against accepted history versus the change a PR would bring to its target branch. [Chromatic branch semantics](https://www.chromatic.com/docs/branching-and-baselines/)

## GitHub building blocks and limits

GitHub Actions artifacts persist build output beyond a job. `upload-artifact` v4 artifacts are immutable after upload, but `overwrite: true` deletes the old artifact and creates a new ID. The action exposes an artifact ID, URL, and SHA-256 digest. The URL lasts only while the artifact, run, and repository still exist; artifacts also expire under retention settings. Cross-run download requires an explicit run or artifact identifier and a token with sufficient access. These properties suit a PR candidate handoff, but do not make an Actions artifact an enduring approved reference. [Workflow artifacts](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts), [upload-artifact source](https://github.com/actions/upload-artifact/blob/main/README.md), [download-artifact source](https://github.com/actions/download-artifact/blob/main/README.md), [artifact retention](https://docs.github.com/en/actions/tutorials/store-and-share-data), [artifact deletion](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/remove-workflow-artifacts)

GitHub's issue-comment API can create and update a PR timeline comment, and its label API can add or remove PR labels. `pull_request` supports `labeled`, `unlabeled`, and `synchronize` events, so a label can request a new evaluation. A label alone is not an approval tied to a particular artifact or head commit. Required status checks are the merge gate; GitHub allows a required check to be restricted to a selected app source. Creating a custom Checks API run requires a GitHub App, while GitHub Actions jobs can provide checks without one. [Issue comments API](https://docs.github.com/en/rest/issues/comments), [labels API](https://docs.github.com/en/rest/issues/labels), [workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), [protected branch checks](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [Checks API guide](https://docs.github.com/en/rest/guides/using-the-rest-api-to-interact-with-checks)

## Recommendation for this repository

The repository already commits generated `.g.cs` golden files beside `.api.txt` signatures and has a `/update-golden` PR command; its API gate separately requires catalogue and ledger entries for surface changes. [Generated API baselines](17-GENERATED-API-BASELINES.md), [API change contract](18-API-CHANGE-CONTRACT.md)

1. Generate the PR candidate deterministically. Upload the candidate bundle and a manifest containing the PR head SHA, base SHA, generator version, file list, and per-file digests. Compare it with the **approved baseline from `main`**, not with the preceding PR run. Include generated docs and reference artifacts under the same manifest if they need approval.
2. Keep one bot-owned PR comment current with a summary, diff links, candidate artifact ID, baseline identity, and the exact approval action. A label such as `approve-baseline` can request promotion, but the evaluating job must verify the approver's authority and bind approval to the candidate digest and head SHA. On a new push, regenerate and require a fresh decision if those values change.
3. Make a dedicated required check fail or remain pending until either output matches the approved baseline or the exact candidate is approved. For an override, record who approved which digest and why. The check should recompute the verdict from durable state, so reruns and label changes cannot silently reuse a stale approval.
4. Test a `main`-artifact baseline for the next PR. Publish an approved capture bundle from the successful `main` run and select it by the exact base SHA. Publish the PR candidate separately. This removes baseline-update commits from the PR. If the `main` artifact has expired, fail with a named "baseline unavailable" result rather than treating the PR capture as approved. Either regenerate a trusted `main` bundle under the pinned toolchain or use a longer-lived versioned store. GitHub documents artifact expiry, so a `main` run artifact needs a recovery plan. [Downloading workflow artifacts](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts)

This experiment fits large images and generated reference documents better than small text contracts. Moving `.api.txt` out of Git would change the local `PARQAPI001` build contract: a local build would need a downloaded reference or a new approval mechanism. Keep that decision separate from the artifact transport. [Generated API baselines](17-GENERATED-API-BASELINES.md), [API change contract](18-API-CHANGE-CONTRACT.md)

These are proposed controls, not built-in GitHub label semantics. If an approval job has write access, keep its handling of PR artifacts as data: GitHub warns that privileged `pull_request_target` workflows must not execute untrusted PR code, and `workflow_run` consumers must treat uploaded artifacts with caution. [GitHub Actions secure use](https://docs.github.com/en/actions/reference/security/secure-use), [pull_request_target guidance](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)
