# 50 - Generated Code Analysis

> Companion to [22](./22-GENERATED-CODE-METRICS.md). Page 22 measures the emitted code; this page
> **lints** it. Both run over the same golden models ([17](./17-GENERATED-API-BASELINES.md)).

## The problem

The emitted code is what consumers compile and run, but until now none of the repository's
analyzers ever looked at it. The analyzers were active, and three things still kept them off it:

1. **The strict rules cover the generator's source, not its output.** `CA2007`, `MA0004` and the
   metric gates are enabled for `src/**.cs`. The emitted code lives inside string literals in
   `CodeEmitter.cs`, so an `await` in a `$"..."` string is invisible to them.
2. **Emitted code only compiled where the rules were off.** In this repository generated code only
   materialises in test, sample and benchmark projects, and `Directory.Build.props` puts
   `CA2007;MA0004` (and more) in `NoWarn` for exactly those projects.
3. **Analyzers skip generated code anyway.** Every emitter writes `// <auto-generated />`, the files
   are named `*.g.cs`, and Roslyn classifies them as generated, so NetAnalyzers, Meziantou and
   Roslynator do not report on them.

The result: [#418](https://github.com/rtkelly13/Parquet.SourceGenerator/issues/418) (roughly 85% of
emitted awaits lack `ConfigureAwait(false)`) went unnoticed for as long as the analyzers had been
switched on. The first run of this analysis reports 525 instances.

## How it works

The analysis is two ordinary builds:

| Project | Compiles | Against |
|---|---|---|
| `analysis/GeneratedCode.Modern` | every `*ParquetExtensions.g.cs` golden model | Parquet.Net 6.1.0, Apache.Arrow |
| `analysis/GeneratedCode.Legacy` | every `*ParquetLegacyExtensions.g.cs` golden model | Parquet.Net 4.25.0 |

Each build compiles the emitted source with the `GoldenModels/` declarations it extends, the same
pairing [22](./22-GENERATED-CODE-METRICS.md) uses. It gets the analyzers a `src/` project gets:

- **the analyzer packages and settings from `Directory.Build.props`**: NetAnalyzers at
  `AnalysisLevel` 9.0-recommended, Meziantou, Roslynator, and
  `EnforceCodeStyleInBuild`;
- **the `src/` `.editorconfig` section**: the section header is
  `[{src,analysis/*/obj/golden}/**.cs]`, so `CA2007`, `MA0004`, `CA1502`/`CA1505`/`CA1506` and every
  later rule added there apply to emitted code without being listed twice;
- **`CodeMetricsConfig.txt`**, so the metric rules use the `src/` thresholds;
- **plus the trim and AOT analyzers** (`IsAotCompatible`), because consumers publish the generated
  code with NativeAOT.

Two switches undo the generated-code exemption:

1. `analysis/Directory.Build.targets` copies the golden files into `analysis/<project>/obj/golden/`.
   `.editorconfig` sections match on a file's real path, and CI publishes the golden files
   outside the repository, so they have to be copied somewhere with a known path.
2. `.editorconfig` sets `generated_code = false` for that path. This overrides both Roslyn
   heuristics, the `.g.cs` name and the `<auto-generated>` header.

Each switch was verified with a probe file carrying an `<auto-generated>` header and a `.g.cs`
name. The probe violated one rule from each analyzer (`CS0219`, `MA0140`, `RCS1163`; it also
carried Sonar rules until [55](./55-SONAR-REMOVAL.md) removed that package). Without the relevant
switch, that analyzer stayed silent.

The `GoldenModels/` declarations are scaffolding, not output. `.editorconfig` turns their analyzer
diagnostics off with `dotnet_analyzer_diagnostic.severity = none`. It does not mark them
`generated_code = true`, because that also drops their nullable annotation context (`CS8669`).

## The gate and the baseline

**The baseline is empty, and it stays empty.** The first run found 1,468 findings in 20 rules.
Waves 1 to 3 of [#554](https://github.com/rtkelly13/Parquet.SourceGenerator/issues/554) fixed the
emitters, and `analysis/GeneratedCodeBaseline.props` (the `WarningsNotAsErrors` list) now names no
rule. Every analyzer warning is a build error for both projects (`TreatWarningsAsErrors`), and
`scripts/GeneratedCodeAnalysis.cs` fails on **any** finding, whether or not a rule is listed. A
line added to the baseline therefore turns nothing green.

In CI the `generated-analysis` job in `.github/workflows/ci.yml` publishes the golden outputs,
runs the script and uploads `generated-diagnostics.txt`. The required `build` check aggregates it
with `test` and `derived`, so a red `generated-analysis` blocks the merge.

**Handling a new finding: fix the emitter.** A finding is an emitter regression. Find the emitted
line, then the string in `src/**/Emitter/` that writes it, and change that. Do not add the rule to
the baseline, to `NoWarn`, or downgrade it in `.editorconfig`. A rule the emitter breaks *on
purpose* is the one exception: it belongs in the `.editorconfig` generated-code section with its
reason written next to it, as a reviewed decision.

### It cannot pass by examining nothing

The script fails, not passes, when:

- the golden directory holds a different number of `*.g.cs` files than there are model
  declarations in `test/Parquet.SourceGenerator.Tests/GoldenModels/` (7: six modern, one legacy);
- either backend compiled no emitted file, or the two together compiled a different number;
- a build left no SARIF log, or failed without reporting a finding.

The positive control is `dotnet run scripts/GeneratedCodeAnalysis.cs -- --self-test`, and CI runs
it before the real analysis. It runs the same pipeline over a seeded golden directory whose two
files each `await` without `ConfigureAwait(false)`, and succeeds only if the gate fails and names
`CA2007` for both backends. A gate that stopped seeing anything would fail that step.

### The emitted code is compiled bare

`analysis/Directory.Build.props` sets `ImplicitUsings` to `disable`, although the repository
default is `enable`. Emitted code has no `using` directives, and consumers need not enable
implicit usings, so the analysis compiles it as it ships. With them on, an unqualified `AsMemory`
compiled in the harness and then failed in package consumption CI (fixed in #556).

## Running and reading it

```bash
dotnet test test/Parquet.SourceGenerator.Tests --filter GoldenCodeGenRegressionTests   # publish artifacts/golden/
dotnet run scripts/GeneratedCodeAnalysis.cs                                           # the gate
dotnet run scripts/GeneratedCodeAnalysis.cs -- --self-test                             # the positive control
```

It takes about 20 seconds after the test project is built. Options: `--golden <dir>`,
`--out <dir>`, `--summary <file>`. Exit code 0 is clean; 1 is a finding or an invalid run.

A failure lists each rule with its count and description, then up to five `file:line` locations per
rule. The line is in the **emitted** file, a copy under
`analysis/GeneratedCode.Modern/obj/golden/` (or `.Legacy`), so open that copy to see the
line. To see every finding as an ordinary compiler warning, build one project:

```bash
dotnet build analysis/GeneratedCode.Modern/GeneratedCode.Modern.csproj
```

It writes `artifacts/analysis/generated-diagnostics.txt` (gitignored, never committed; CI uploads it
as the `generated-diagnostics` artifact):

```
# examined 7 emitted files (legacy 1, modern 6)
# total 0
```

Findings follow, per rule with a count, then per golden model. The script counts only
`warning`/`error` results; the SARIF log also records suggestion-level ones, which the build does
not report.

## Lessons from clearing the first run

- **Class-coupling headroom (`CA1506`).** The type threshold in `CodeMetricsConfig.txt` is 95.
  `OrderEventParquetExtensions`, the most coupled golden model, is coupled with 88 types on `main`
  at `d0cb7d9` (measured with the threshold lowered to 50; the others are 76 to 84). The #418
  change (#557) had to dispose emitted readers and writers via `try`/`finally` instead of
  `await using` to stay under the limit. Every extra type the emitter references costs headroom,
  so a fix that adds helper calls on every column can trip `CA1506` while clearing another rule.
- **Parallel lanes share files.** #555, #557, #558 and #560 all edited `Emitter/CodeEmitter.cs`,
  and #556, #557 and #558 edited emitters under `Emitter/Components/`. Each lane was verified
  against the harness on its own branch, so a green lane says nothing about the merge of two. Run
  the analysis again after a rebase onto a `main` that has moved.
- **Review bots repeat two findings.** The same two fixes recur in the review commits of #555
  and #557 (drop the `$` on emitted no-hole interpolated strings) and in #555, #556 and #557 (add an
  `Async` suffix to Task-returning tests).

## Not covered

- **Formatting.** CSharpier is a formatter, not an analyzer. The emitted code is deliberately dense
  (several statements per line), so a format check would only restate that choice.
- **Duplication.** [23](./23-DUPLICATION.md) excludes emitted code by design.
- **Models outside the golden corpus.** The analysis covers what the golden models emit. An
  emitter branch no golden model reaches is not analysed; the fix is a golden model that reaches
  it.
